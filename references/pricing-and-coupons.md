# 定价与优惠券口径（踩坑清单）

## 1. 金额单位

| 来源 | 单位 | 处理 |
| --- | --- | --- |
| `query-meals.currentPrice` / `originalPrice` | 元（字符串） | 解析后 ×100 转分 |
| `calculate-price` 全部金额字段 | **分**（整数） | 直接使用，展示时 ÷100 |
| `query-meal-detail.choices[].diffPrice` | `"+ ¥0"` / `"- ¥1"` 文本 | 去符号后 ×100，注意全角减号 |

内部一律用「分」做整数运算，避免浮点误差。

## 2. 实付的组成

```
实付 = 商品现价 + 运费 + 打包费 − 优惠
```

- 到店：无运费、无打包费。
- 外送（麦乐送/团餐）：实测运费 600 分、打包费 110 分（不同门店/时段可能不同，以核价返回为准）。
- **打包服务费行**：外送 `productList` 里会出现 `920174 打包服务费`（实测 quantity=11、originalSubtotal=110），它已被计入 `price`，自己再加一遍就多算 ¥1.1。
- 优惠以 `discount` 字段为准；`price` 已经是优惠后的实付。

## 3. 折扣类型语义（`enjoyed/ enjoyable`）

| amountType | 含义 | realDiscount 示例 |
| --- | --- | --- |
| 1 | 特价 | 18（该商品特价 18 元） |
| 2 | 折扣 | 7.5（7.5 折） |
| 3 | 立减 | 5（减 5 元） |

`balance` = 门槛差额（分）。若 `enjoyable.balance=800` 说明「再买 8 元可享该优惠」，可用来做「凑单提示」，但**凑单后必须重新核价**验证是否真的更便宜。

## 4. 券的三类约束

| 约束 | 数据来源 | 判定方式 |
| --- | --- | --- |
| 时效 | `query-my-coupons` 有效期 + 可用时段 | `now-time-info` 比对；时段如 10:00–22:00、周日 05:00–10:29 |
| 渠道 | 券标签「到店专用 / 外送专用」 | 到店/DT 用「到店」券；麦乐送/团餐用「外送」券 |
| 商品/门店 | 只能靠试算 | `calculate-price` 传 `couponId`+`couponCode`；`600012`=不可用 |

**不要**用 `query-store-coupons` 的空数组反推「没有可用券」——实测出现过券包有 3 张、门店可用券接口返回空的情况。

## 5. 券试算的成本控制

每次试算 = 一次 `calculate-price` 调用。建议：

1. 只对**最便宜的 2~3 个候选**试算；
2. 同一张券试一次即可（同一候选组合）；
3. 单次对话核价调用总数建议 ≤ 32 次，超了就先给方案并说明「券未全部验证」。

## 6. 省额的计算口径

- **同款跨渠道省额**：同一组商品（按名称对齐后）在各渠道的**实付**最大值 − 本方案实付。
- **用券省额**：同候选「无券实付 − 有券实付」，两者都必须是核价结果。
- 不要拿「菜单价对比」当省额，也不要拿「原价 − 实付」冒充跨渠道差价。

## 7. 常见错误示范

| ❌ 错误做法 | 后果 |
| --- | --- |
| 拿菜单价当实付 | 外送少算 ¥7.1（运费+打包），结论可能反过来 |
| 用 productCode 跨渠道匹配 | `60006` 商品不可售，或匹配到完全不同的商品 |
| 券包显示可用就计入优惠 | 结账时 `600012`，承诺的优惠不生效 |
| 把 `status=2` 的积分商品当可兑换 | 商品早已下架（`downTime` 已过） |
| 积分 0 还推荐抽奖 | `resourceEligible=false`，抽不了 |
| 到店下单不传 `takeWayCode` | 下单失败 |
| 用自己估算的时间判断券时段 | 券在非时段内不可用 |
