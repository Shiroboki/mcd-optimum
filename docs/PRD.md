## 1. 背景与问题

麦当劳官方 MCP 暴露 35 个工具，覆盖菜单、核价、门店、券、积分、抽奖、商城、团餐、派对等。
但**用户真正的决策问题是**：*「按我的预算、口味、热量目标，今天怎么买麦麦最划算，而且券真的能用？」*

实测发现四层信息断裂（证据见 SMOKE_TEST_REPORT）：

1. `productCode` 跨渠道不通用 → 无法直接比价。
2. 渠道费用与可用性差异大（同款差 ¥11.10）；得来速可能没有数据。
3. 券可用性受「门店×渠道×商品×时段」四维约束，实测 3 张券全部不可用。
4. 套餐换选 / 特调 / 营养约束会改变最优解。

现有公开作品多集中在「菜品推荐」与「自动下单流水线」，**缺少一个把渠道、资产、组合统一求解并给出可验证解释的决策层**。

## 2. 目标与非目标

### 目标
- G1：给定意图（预算 / 热量上限 / 必含商品 / 门店），输出 3~6 套**按实付升序**的方案。
- G2：每个方案的价格**必须**由 `calculate-price` 真实核价，禁止估算。
- G3：券在**下单前**完成核销判定，给出可用/不可用与原因。
- G4：输出可回放的脱敏调用链，证明「真的用了 MCP」。
- G5：默认 dry-run，写操作需显式确认。

### 非目标
- 不做自动支付、不做无人值守下单、不做多账号聚合。
- 不做积分兑换/抽奖的自动执行（实测账号积分为 0，无法验证）。
- 不做非官方数据源（不爬取、不接入第三方比价平台）。

## 4. 功能需求

### P0（必须完成，截止前必须全绿）

| ID | 需求 | MCP 工具 | 验收标准 |
| --- | --- | --- | --- |
| F1 | 渠道探测 + 自动降级 | `query-nearby-stores`、`delivery-query-stores` | DT 失败（600047/600050）时其余渠道继续，diagnostics 有说明 |
| F2 | 跨渠道商品实体对齐 | `query-meals` | 同款商品在两渠道被识别为同一实体，单测覆盖 |
| F3 | 组合候选生成 + 硬约束 | `query-meals`、`list-nutrition-foods` | 预算/热量/必含商品过滤生效，候选数受剪枝上限控制 |
| F4 | 官方核价复核 | `calculate-price` | 所有展示价格来自核价返回；行级金额剔除打包服务费重复项 |
| F5 | 券四维核销判定 | `query-my-coupons`、`query-store-coupons`、`calculate-price` | 券可用时计入实付；不可用时记录业务码；`couponId+couponCode` 双传 |
| F6 | 方案排序 + 解释链 | — | 按实付升序；每方案有 ≥2 条可读解释 |
| F7 | dry-run 与 orderDraft | —（不调用 `create-order`） | 页面明确标注不产生真实订单 |
| F8 | 脱敏调用链 | 全部 | trace 中无 token/手机号/地址/券码 |
| F9 | mock 模式 | — | 无凭据启动并跑通完整链路 |
| F10 | 5 份必备文件 | — | README / CONTEST_DECLARATION / MCP_INTEGRATION / mcp-config.example.json / workbuddy.md |

### P1（时间允许则做）

| ID | 需求 | 价值 |
| --- | --- | --- |
| F11 | 特调层（`query-meal-detail` 的 `selectedKey/unselectedKey`） | 去酱/去冰/换选参与优化 |

- 派对 / 品鉴会预约（`party-*`）
- 多门店批量比价

## 7. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 得来速无数据 | 少一个渠道 | 已实现探测+降级，文档如实说明 |
| 积分为 0 | 无法演示兑换 | 降级为体检，不承诺执行 |
| 券全部不可用 | demo 无「省钱」高光 | 把「不可用判定」本身作为卖点，并用跨渠道价差体现省钱 |
| 核价接口限频 | 候选不能穷举 | 剪枝 + 预算护栏 + LRU 缓存（D3 补） |
| 商品名不规范 | 对齐错误 | 别名表 + 最短匹配 + 单测；宁可不匹配也不乱匹配 |
| 时间不足 | 功能不完整 | P0 优先；P1 只做「特调层」一个点 |
